# law-api — 법제처 법령정보 Open API 수집 (W6)

법제처 국가법령정보 Open API로 **검색 → 법령ID → 본문 → FastAPI 서버 → SQLite 캐시** 파이프라인을 만든 실습.

| 파일 | 역할 |
|---|---|
| `step1_search.py` | 목록조회(`lawSearch.do`)로 법령 검색 → 법령ID |
| `step2_detail.py` | 본문조회(`lawService.do`)로 법령ID의 현행 조문 조회 |
| `law_client.py` | 검색·본문조회 재사용 함수 (`search_law`, `get_law_detail`), 인증키는 `.env`에서 읽음 |
| `explore.py` | 응답 JSON을 들여쓰기로 출력해 구조 확인 |
| `main.py` | FastAPI 서버 (`/search`, `/detail/{law_id}`) + DB 캐시 |
| `db.py` | SQLite `laws`·`articles` 테이블 생성·저장·조회 |

실행: `.env`에 `LAW_OC=본인OC` 한 줄을 넣고 `uvicorn main:app --reload` → http://127.0.0.1:8000/docs

## ① 결과 확인

- `search_law("전자금융거래법")` → `전자금융거래법 / 010199`, `전자금융거래법 시행령 / 010366`
- `get_law_detail("010199")` → `제1장 총칙`, `제1조(목적) 이 법은 전자금융거래의 …`, `제2조(정의) …` 순으로 조문 80개
- explore 출력에서 `"법령일련번호": "290247"`과 `"법령ID": "010199"`가 서로 다른 값으로 따로 있음을 확인
- `/detail/010366`을 두 번 호출
  - 1회차: `"source": "api(law.go.kr)"`, `article_count: 54`
  - 2회차: `"source": "db(cache)"`, `fetched_at` 표시 → 법제처를 다시 부르지 않고 DB에서 응답

## ② 핵심 개념 되새김

- **인증키(OC)가 하는 일**: 법제처가 "누가, 어느 IP에서, 승인받고 부르는지"를 확인하는 신분증이다. 서버는 요청을 하나씩 따로 처리하고 이전 요청을 기억하지 않기 때문에 요청마다 붙여야 한다. 틀리면 결과 0건이 아니라 `{"result": ...}` 오류 JSON이 온다.
- **목록조회 → 본문조회 2단 호출**: 목록조회(`lawSearch.do`)는 검색어로 법령명·법령ID 같은 요약만 주고, 본문조회(`lawService.do`)는 법령ID 하나로 조문 전체를 준다. 검색 결과 전부의 본문을 한 번에 받으면 너무 무거워서, 먼저 골라내고 필요한 것만 자세히 가져오는 구조다.
- **DB에 캐시하는 이유**: 같은 법령을 다시 부를 때 법제처를 또 호출하지 않아도 되니 응답이 빠르고 호출량 제한도 아낀다. 받은 시각(`fetched_at`)과 함께 저장해 두면 이력도 남는다.

### 단계별 기록

- **단계 0 · OC**: 본인 OC는 아직 승인 전이라 공용 데모 계정 `test`로 진행했다. 승인되면 `.env`의 `LAW_OC`를 본인 값으로 바꾼다.
- **단계 1 · 검색 결과**: 전자금융거래법 / 법령ID `010199`
- **단계 2 · 본문조회를 따로 부르는 이유**: 목록조회는 법령명·법령ID 같은 요약만 주고 조문 내용은 주지 않는다. 조문은 법령ID를 넘겨 본문조회를 불러야만 받을 수 있다.
- **단계 3 · 법령ID vs 법령일련번호**: 법령ID(`010199`)는 법 자체의 번호라 개정돼도 그대로이고, 법령일련번호(MST, `290247`)는 개정본마다 새로 붙는다. 본문조회에는 법령ID를 넣어야 늘 현행본이 온다.
- **단계 4**
  - 함수 재사용으로 다시 짜지 않아도 된 것: URL·파라미터 조립, 오류 JSON 검사, "1건이면 딕셔너리" 처리, 결과 파싱을 `main.py`에서 다시 쓰지 않았다.
  - `/docs`를 만든 것: FastAPI가 함수의 경로(`@app.get`)와 타입 힌트(`query: str`)를 읽어 자동으로 만들었다.
- **단계 5**
  - 두 번째 요청에서 법제처를 부르지 않은 이유: 첫 요청 때 `save_law`로 저장해 둔 것을 `load_law`가 찾아 바로 응답했다.
  - `save_law`를 지우면 캐시가 안 되는 이유: 저장을 안 하니 다음 요청 때 DB에 찾을 것이 없어 매번 API를 부른다. 캐시는 읽기와 쓰기가 한 짝이다.

## ③ 자유 로그

- **오늘 배운 것**: 크롤링(5주차)과 달리 공식 API는 응답 구조가 정해져 있어 안정적이다. 대신 인증키·IP 등록·승인 같은 준비 과정이 필요하다. `explore.py`처럼 응답을 먼저 통째로 찍어 보고 코드를 짜는 습관이 KeyError를 막아 준다.
- **막힌 곳과 푼 과정**
  - 본인 OC 승인이 아직 안 나서 `test` 계정으로 진행했다.
  - GitHub push 때 `law-api` 저장소가 없어서 실패했다. 저장소를 먼저 만들고, 원격 주소 연결(`git remote add`) 후 push해서 해결했다.
  - 다른 폴더에서 연결했던 GitHub MCP가 여기서는 안 보였다. MCP 설정은 폴더별로 저장된다는 것을 알게 됐다.
  - 7주차 준비로 WSL과 Docker Desktop을 설치했고, `docker run hello-world`로 동작을 확인했다.
- **아직 안 풀린 것**
  - 조문이 제목·첫 줄만 나오고 항·호 본문은 빠진다(교재 4장 심화).
  - 목록조회가 기본 20건까지만 와서, `display`·`page`로 전부 모으는 부분은 아직 안 해 봤다.
- **AI 활용**: Claude Code에게 실습 코드 실행 검증(단계 1~5), 이 README 초안, git 커밋과 GitHub 저장소 생성·업로드를 맡겼다. 각 단계 출력이 워크북의 "확인" 기준과 일치하는지, GitHub에 `.env`가 올라가지 않았는지 직접 대조해 검증했다.

## 응답 구조 확인 기록 (explore.py 요약)

`{"LawSearch": {"law": [ {...}, {...} ]}}` 형태이고, 항목 하나에 키 16개가 있다. 이 중 `법령명한글`, `법령ID`, `법령일련번호`를 사용했다. 법령일련번호는 항목 위쪽에, 법령ID는 열 줄쯤 아래에 떨어져 있다. 본문조회 응답은 `{"법령": {"조문": {"조문단위": [...]}}}` 구조이고, 각 조문의 `조문내용`만 꺼냈다.
